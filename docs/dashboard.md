# フロー監視画面

ローカルのジョブ状態を、Issue単位のフローとして表示します。

```sh
.venv/bin/python -m ado --config config.toml dashboard
```

ブラウザで http://127.0.0.1:8765/ を開いてください。ポートを変える場合は `dashboard --port 8766` を指定します。終了はCtrl-Cです。workerは従来どおり別のターミナルやlaunchdから起動します。dashboardを起動するだけでworkerが動き始めることはありません。

## 見られる内容

- 左：プロジェクト別のIssue一覧、保存された状態、workerの最終応答。
- 中央：仕様確認→資料取得→MiniMax実装→変更検査→PR作成→CI→レビュー→人間の確認→完了。現在の工程と修正ループを表示。
- 上：Issueのタイトルと「何をしているか」の短い説明。例：READMEの導入手順に沿ってMiniMaxが変更案を生成中。
- 右：クリックした工程の説明、待機・停止理由、モデル呼出し回数、修正回数、変更ファイル名、Issue/PRリンク。
- 下：最近の工程遷移と時刻。

3秒ごとに更新します。ズーム・ドラッグ・全体表示・現在地への移動が使えます。狭い画面では現在の工程を拡大して表示します。

## 実データとデモ

画面の「デモを見る」で、レビュー待ち・実装中・停止・完了のサンプルを確認できます。デモはサーバーのメモリ上で生成し、実ジョブ・SQLite・監査ログには保存しません。「実データに戻る」で設定したstate_dirの表示に戻ります。

dry-runのスキャン結果は「dry-run確認済み」として表示し、ライブジョブとは区別します。実装やPR公開を行った表示にはしません。

## 状態の読み方

フローの「現在地」は最後に保存・記録された工程です。workerが生きていることと同じ意味ではありません。新しいworkerは5秒ごとに稼働情報を記録し、15秒以上応答がなければ画面で応答なしと表示します。古いworkerのstateも表示できますが、詳細工程・タイトル・稼働情報がない場合は保存状態とIssue番号を使います。完全な工程履歴を得るには更新後のworkerを使用してください。

工程の通過表示は現在の処理順に基づきます。修正ループが発生した場合は修正回数と履歴も確認してください。ログの読取りは末尾512KiB・最大1000イベント、表示は最新200ジョブ・各60イベントに制限しています。

## 接続とデータ

サーバーは127.0.0.1にだけ接続し、設定されたSQLiteを読み取り専用で開きます。GitHub APIやモデルは呼びません。追加のPython依存・Node.js常駐プロセス・クラウドサービスは不要です。ブラウザ用アセットもローカルから配信します。

画面用APIは表示に必要な項目だけを返し、プロンプト・変更内容の全文・認証情報・MiniMaxの設定パスは返しません。タイトルと理由は既存の秘密パターンでマスキングします。変更ファイル名・Issueタイトル・PR情報は画面に表示されるため、画面共有時はその内容を確認してください。

`/api/status`が実データ、`/api/demo`がデモです。操作APIはなく、再試行・マージ・設定変更は従来のCLI/GitHubで行います。
