# オペレーターランブック

ADOの実行処理が保存した状態と理由から、オーケストレーターの動作と必要な運用対応を確認します。ダッシュボードは読み取り専用で、workerとは独立して動作します。

## QUEUED

- **オーケストレーターが行っていること**: 適格なIssueをローカルで予約している。dry-runのスキャンではライブジョブを予約しない。
- **運用者が次にすべきこと**: 通常は待つだけでよい。dry-runでスキャン結果を画面で確認した後は、ライブジョブを待つ必要がない。

## BUILDING

- **オーケストレーターが行っていること**: 呼出し予算を確保し、許可されたIssueテキストから変更案を生成している。不合格になった変更の修正も、この状態の生成処理で行う。呼出し予算は `1 + max_repairs` 回で、`max_repairs` の既定値・上限はともに3である。
- **運用者が次にすべきこと**: 変更生成が終わるまで待つだけでよい。その間、画面で確認できる現在の説明、モデル呼出し回数、修正回数、workerの稼働状況を確認する。

## PUBLISHING

- **オーケストレーターが行っていること**: 変更内容とcommit意図を保存し、専用ブランチやPRの作成など、公開処理を再開できる状態にある。
- **運用者が次にすべきこと**: 公開処理が進むまで待つだけでよい。処理が進まない場合は、画面に表示されるIssue・PRリンク、workerの稼働状況、ログを確認する。

## REVIEW

- **オーケストレーターが行っていること**: 同一のhead SHAに対するCIと、選択したレビュアーの判定を待っている。不合格があれば修正ループを実行する。修正は初回生成の後に `max_repairs` 回まで行われ、`max_repairs` の既定値・上限はともに3である。モデル呼出しは初回生成を含めて最大4回である。
- **運用者が次にすべきこと**: CI、レビュー、修正履歴を確認しながら待つだけでよい。失敗、期限、呼出し予算や修正上限に達した場合は`BLOCKED`になるため、停止理由を確認する。

## AWAITING_HUMAN

- **オーケストレーターが行っていること**: 判定に合格した変更について、自動マージが無効である場合などに人間を待っている。
- **運用者が次にすべきこと**: PRの差分、CI、レビュー結果を確認し、基準を満たす場合だけGitHub上でマージする。ダッシュボードにはマージ操作がない。マージ後、オーケストレーターがマージ済みであることとIssueの完了を確認する。

## BLOCKED

- **オーケストレーターが行っていること**: 失敗、期限、安全基準、上限、または依存追加・設定変更によって停止している。停止したジョブは自動再試行しない。launchdのプロセスが再起動しても、保存された`BLOCKED`のジョブは再開しない。
- **運用者が次にすべきこと**: 停止理由、状態、workerのログを確認する。原因が解消しても、無条件に同じジョブを再開できるとは限らない。モデル／レビュー呼び出しの中断は、後述の手順で既存アーティファクトを確認し、新しいIssueとして依頼する。その他の失敗も、再実行が許可されることを確認してから明示的な運用操作を行う。

## DONE

- **オーケストレーターが行っていること**: 実際のマージを確認し、対象Issueを完了扱いにしている。
- **運用者が次にすべきこと**: 待つ必要はなく、通常は追加対応もない。必要に応じて、status表示やダッシュボードで完了を確認する。

## BLOCKEDになり得る状況と運用者の対応

`BLOCKED`のジョブは自動再試行しない。再試行可能な失敗と、中断されたモデル／レビュー呼び出しを区別してください。下の「明示的な再実行」は、該当ジョブの再開が許可される失敗で、運用者が実行可否を確認した場合に限ります。

| 状況 | 確認する内容 | 運用者の対応 |
|---|---|---|
| Issueの適格性・受入条件・依存Issueの不備 | 作成者、`ado:ready`、受入条件、依存Issueの状態を確認する。 | 不備を解消し、実行が許可されることを確認してから明示的に再実行する。自動再試行はしない。 |
| 変更検査の失敗 | 許可された変更パス、内容、機密情報、変更量を検査結果と照合する。 | 許可範囲内の作業に整理するか、対象を別の作業に分ける。原因と実行可否を確認してから再実行する。 |
| 依存追加または設定変更 | 保護された依存マニフェストを含む依存追加・設定変更が含まれていないか確認する。 | このジョブでは続行しない。該当変更を別の作業として用意する。 |
| CI・レビュー不合格が解消できない | check summary、conclusion、レビュー本文、未解決スレッドを確認する。 | 不合格内容を修正入力として扱う。修正できずに上限へ達した場合は、停止後に対応する。 |
| 呼出し予算または修正上限 | 画面に表示されるモデル呼出し回数と修正回数、利用契約を確認する。 | 上限を使い切ると自動続行しない。`ado retry` で再開しても追加のモデル呼出しは発生せず、直ちに `BLOCKED` に戻る。同じジョブの再試行ではなく、契約枠と次回予算を確認し、新しいIssueとして依頼する。 |
| 期限超過 | 経過時間、最近の工程遷移、停止理由を確認する。 | 期限済み処理を継続させず、原因を解消してから新しい実行操作を行う。 |
| パッチのアンカーが見つからない、または一意でない | 停止理由（`Patch anchor is not unique in <path>: N matches`）と、対象ファイルの該当部分を確認する。 | 理由はモデルにそのまま渡され、修正1回として同じジョブで再試行されます。予算を使い切ったら、対象箇所の文言を確定させてから新しいIssueとして依頼する。 |
| GitHub API、CLIログイン、モデル呼出し、契約枠に関する失敗 | 停止理由とworkerのログを確認する。CLI互換性の診断と、ログイン・モデル呼出し・契約上限の確認をそれぞれ行う。 | 原因を解消し、再実行が許可されることを確認してから明示的に再実行する。 |
| モデル／レビュー呼び出しの中断 | 停止理由が`Interrupted model/review call; automatic replay forbidden`になっているか確認する。既存アーティファクト、Issue・PR、監査イベント、可能なCI・レビュー結果を確認する。 | 障害を直しても同じジョブの再開では復旧できない。既存アーティファクトを確認したうえで、新しいIssueを作成して別のジョブとして依頼する。 |

CodeRabbitがAPPROVEDを返さない場合は、レビュー本文の自然言語を承認と推測しません。実際の判定と停止理由を確認します。

ダッシュボードの「応答なし」は、保存された現在地だけで判断します。15秒以上応答がないことは、保存された工程がworkerの稼働を保証しないことを示します。状態、worker、launchdのログを確認し、続いて失敗や期限に達した場合に`BLOCKED`として扱います。

## 無人運転を有効にしない

次の2つを同時に設定し、「無人運転を有効にしない」構成にします。

- `dry_run = true`: Issueの取得、仕様と依存関係の検査だけを行います。モデル呼出し、GitHubへの書き込み、ライブジョブの予約は行いません。公開リポジトリの読み取りには既存の `gh auth login` を利用できる。`scripts/launch.py` は dry-run では `GH_TOKEN` を子プロセスへ渡さないため、`gh` は保存済み認証情報をKeychainから読み取ることがあります。
- `auto_merge = false`: 判定に合格した変更も、人がGitHub上でマージするのを待ちます。

この2つを設定することで、無人運転を有効にしない運用を維持できます。
